Chapter 2. Architecture Overview

This chapter gives you a short introduction to the overall architecture of the HTTP Secure Proxy.

2.1. Overview

The HTTP Secure Proxy is a HTTP reverse proxy that protects web applications by providing externalization of authentication to a specific login service, i.e. the HTTP Secure Proxy does not perform authentication itself but intercepts each client request and validates its access rights.

One of the advantage of the HTTP Secure Proxy is its focus on use of non-intrusive, standardized methods for the interfaces between all involved components, which are shown in the following image:

Figure 2.1. Architecture overview


The client, also called "initiator", is typically a standard Web browser. A user types in a specific URL protected by a HTTP Secure Proxy, e.g. https://entry.mycompany.com/app/portal.

The HTTP Secure Proxy, called "access control enforcement" above, redirects the request to the Login Service, called "authentication and access control decision function" above.

The login service is responsible for the whole authentication process. When the user has successfully authenticated herself, it redirects the user request back to the original web application URL. It does this by using the interface between the Login Service and the HTTP Secure Proxy, which is solely based on HTTP mechanisms.

At last, the HTTP Secure Proxy allows the request initiated by the client to travel to the web application, called "target" in the image above.

To resume, the HTTP Secure Proxy forwards request and enforces access control based on locations.

2.2. Login Service

While the HTTP Secure Proxy implements access enforcement functions by redirecting the client to the Login Service, the Login Service implements the access control mechanisms by authenticating the client.

The Login Service therefore implements the login process including all necessary dialogs with the client.

2.3. Protection Levels

Each location in the HTTP Secure Proxy can be defined to carry one the access levels defined above by setting a specific directive. Please refer to the Administrator's Guide of the HTTP Secure Proxy for more details about configuration directives.

The following protection levels are possible:

  • Public : A location defined "public" is accessible by all visitors. The HTTP Secure Proxy does not perform access control on it, but simply verifies the HTTP or HTTPS headers to block potential attacks on known security holes in web or application servers.
  • Member : For locations defined "member" level, visitors must typically identify themselves with a so-called "weak" authentication method, e.g. user name and password in order to be able to access the web application behind the location. As described above, the HTTP Secure Proxy checks each request and, if not authenticated yet, redirects the user to the login service. The login service then typically provides a login form with the appropriate authentication mechanism.
  • Customer : The third and most secure level is the "customer" level. A simple user name/password check is insufficient for visitors to gain access. We recommend the use of security certificates or RSA SecurID authentication. It is again the responsibility of the Login Service to grant access to different levels appropriately.

Chapter 3. Interface Overview

The HTTP Secure Proxy uses different interfaces to interact with the Login Service, the application servers and the client. This chapter defines each interface and gives you details and examples about it.

3.1. Overview

Generally, the interfaces between all involved components are based on the HTTP standard. Headers and cookies are used to signal state changes, failures and successes, and to deliver information between the components. The following interfaces

Client interface
the interface between a client, e.g. a Web browser and the HTTP Secure Proxy
Application server interface
the interface between a protected Web application and the HTTP Secure Proxy
Login Service interface
the interface between the Login Service and the HTTP Secure Proxy

An implicit interface exists between the protected Web application and the Login Service as the Login Service delivers authentication, or identity, information to the protected Web application.

3.2. HTTP Headers

3.2.1. Overview

According to [RFCHTTP1.1] supports transmission of special header data that is not directly visible to the Web browser client. Applications can use this extra information for content classification. The HTTP Secure Proxy and the Login Service use HTTP headers for storing control information. Applications and the HTTP Secure Proxy communicate directly via the header data field, while cookies are used between the Web browser client and the HTTP Secure Proxy.

3.2.2. HTTP Secure Proxy Header Filter

The HTTP Secure Proxy filters header data fields, passing only its own fields and external fields that have been explicitly enabled by the administrator. If your Web application needs to receive specific HTTP headers, you need to provide this information to the HTTP Secure Proxy administrator. The person in charge there is then able to configure header names in your location definition as not being blocked.

Regular browsers are generally incapable of handling custom headers, and they only generate headers envisaged by the standard. However, other client types, e.g. Java applications or Web Services clients may set custom headers with each request, hence you must be aware of the HTTP header filter feature of the HTTP Secure Proxy.

3.2.3. SSL-specific Headers

SSL information like Fingerprint, Certificate, SerialNumber, etc. is an important case in point when you want to verify a security certificate (exchanged between the HTTP Secure Proxy and the Login Service web application). Available headers and their potential applications are described in [HTTPADMIN].

3.2.4. Sample Session

The following scenario provides an example of what happens mainly between the HTTP Secure Proxy, the Login Service and the protected Web application. We use Java and the Servlet API standard as the environment for the source code we provide here.

A client enters an URL in the Web browser. The HTTP Secure Proxy intercepts this request and redirects the Web browser to the Login Service. The HTTP Secure Proxy provides the Login Service with different information, e.g. the requested page. Therefore, the Login Service stores this value by reading it from a specific header sent to it:

String requestedPage =
            HttpServletRequest.getHeader("RequestedPage");

The Login Service presents a login form to the user. After successful login, the Login Service sets two headers and redirects the Web browser client to the original URL stored before:

HttpServletResponse.setHeader("AccessArea","Member");
HttpServletResponse.setHeader("LoginUserData",
    "id=bgo;option1=10;option2=blue");
HttpServletResponse.sendRedirect(requestedPage);

By setting the header "AccessArea" to "Member", the Login Services signals a successful authentication back to the HTTP Secure Proxy.

A second header, "LoginUserData", set by the Login Service contains the identity information of the authenticated user. This header is carried forward by the HTTP Secure Proxy with each request that the protected Web application receives.

After this redirect, the HTTP Secure Proxy now receives the redirect to the original URL. The user is now authorized for this location, the HTTP Secure Proxy passes the request to the application server host and port defined in the location, adding the login credentials (provided by the Login Service in the "LoginUserData" header) to each request in the header "LoginCredentials". Therefore, a very simple Web application finds out about the identity of the authenticated user by issuing the following command:

if (no session available yet) {
  String loginCredentials =
      HttpServletRequest.getHeader("LoginCredentials");
  // verify credentials, create session, etc.
  String id = retrieveId(loginCredentials);
  ...
  // create session
  HttpServletRequest.getSession(true);
  // set the user in the application or on
  // container level
  ...
}

It is, of course, better to either use the Java Servlet Filter approach or JAAS for a cleaner, more modular solution. This is, however, not in the scope of this document.

3.3. HTTP Cookies

3.3.1. Setting Cookies

You are able to set, update or remove cookies in the Login Service and in the protected Web applications.

The HTTP Secure Proxy stores client-related cookies in the Client Data Store (CDS). The client only gets a reference to its data items in the CDS. All cookies stored in the Client Data Store are lost after a logout of the user.

It is possible to configure cookies as being "transparent". Such cookies are not stored in the Client Data Store, they are passed through to the client. This feature can be used to persist cookies in the client browser, e.g. for storing default language configuration, specific, not security-relevant user account information. If such cookies are not made "transparent", stored information is lost at each logout.

6.2. Specific Characteristics

The following bullet list contains general remarks about the client interface:

  • Cookies are not passed back and forth through the HSP unless they are configured as "transparent" in the HSP configuration. See the directive SE_IntCookie_PersistentCookies in [HTTPADMIN].
  • Requests using the HTTP transfer encoding type "chunked" (chunked POST) are not supported and will be blocked. POST bodies must use a "Content-Length" header.
  • The HTTP "Server" Header sent by application servers is overwritten by the HSP. The new header content can be configured.
  • The behavior of the HSP can be changed by programmatically setting a specific value to the HTTP "User-Agent" header in the client application. See the documentation about the directives SE_ExtCookie_CookieCheck and SE_ExtSslSid_Supported in [HTTPADMIN] for further information.

6.3. Initial Request [1.1]

The first request to the HSP does not contain any HSP-specific data items. If the all-first request uses the HTTP POST method, the POST data is stored in the post data store of the HSP. After successful cookie check and, if necessary, successful login, the POST data is re-issued to the target URL.

The sentence above is not entirely correct! More precisely behaviour of HSP and SLS is as follows:

If the request contains a RequestedPage parameter as the first GET parameter, the HSP sends req az headers for the location of the RedirectPage. If there is no such RequestedPage header, the HSP determines req az headers for the AuthorizedPath location of the current locaction (i.e. the login location). Corresponding req az headers are then always sent (if there are any).

In SLS <4.20.0 this could cause login models to be reset in the middle due to req az headers being sent again (especially if authorizations were set for the root location "/"). Since SLS 4.20.0, req az headers are only considered if there is a RequestedPage parameter or if it is the first request of the SLS login session, and otherwise ignored.

In combination, this effectively achieves in practice the same effect as what the first sentence above stated.

10.3. Session Attributes

Session attributes are stored within HSP Sessions and customize the behavior of the SRManager for authenticated clients. Session attributes are used to generate HTTP headers, supply parameters to the Adaptive Application Integrator, grant user authorizations or to define a per-user gateway configuration.

These attributes are set through special HTTP response headers by the login service on successful authentication and cleared if the user logs out. The SES also sends existing session attributes to the SLS if an authenticated user accesses the login service again.

10.3.1. When To Create Session Attribute Headers

Note that the SES accepts Session Attribute headers from the SLS only if the SLS also sets the "AccessArea" header at the same time!

10.3.2. Session Attribute Header Syntax

The login service must set a HTTP header with the following syntax in order to create an SES session attribute:

Header name:

HSP_AC_SESSION_ATTRIBUTES-<no>

Where <no> is a numeric counter, beginning with 0 and counting up. The number has no preceeding zeroes. There must be no gaps in the numbering!

Header value:

usage="",name="",path="",value="",vtype="",encoding="",timeout=""

Some of these key/value pairs are mandatory, others are optional. For each key / value pair, the following rules apply:

  • The key must be an alphanumeric string.
  • The value must be a string enclosed in double quotation marks. Any forms of escaping are not supported.

This is a typical example of a Session Attribute header created by the login service:

HSP_AC_SESSION_ATTRIBUTES-1'='usage="prop-header",name="userid",path="/intranet",value="jmiller",encoding="url"

The most important key to note is usage. It defines the semantical meaning of the entire header, and also what the contents of the other keys can or must be. See the following chapters for details.

10.3.3. Usage Types

HTTP Header Propagation (usage="prop-header" )

Session attributes of this usage type cause the SES to generate HTTP headers which are sent to application servers and the Login Service with all subsequent requests after a successful login.

If more than one HTTP Header attribute with the same name match the request's URI, a single HTTP Header is generated where only the most exact match is used.

  • "name" specifies directive name
  • "value" is used as the header content.

Gateway Parameter (usage="gw-param" )

A set of directives in the SRManager Gateways, such as the HTTP 1.1 Gateway, can be set using Attributes of this class.

See [HTTPADMIN] for supported directives.

  • "name" specifies the directive name,
  • "value" specifies the first parameter, leave empty ( "" ) if unused
  • "param" may specify subsequent parameters.

AAI Parameter ( usage="aai-param" )

This type is used to set variables which are retrieved by the Adaptive Application Integrator (AAI). See [HTTPADMIN] for AAI rules.

  • "name" specifies the variable's name,
  • "value" specifies the variable's value

Application Authorization Identifier ( usage="ac-app-az" )

This usage type is used to set the application authorization identifier (az) variables which are used for the per application authorization functions.

Only one application authorization identifier must be set for a location (path) and the name must correspond to the definition in the SRManager. See also the RequireAz command directive in [HTTPADMIN].

  • "name" string which specifies the application authorization identifier
  • "value" = "allow"
  • Optional "timeout" in seconds to specify idle timeout of this authorization

10.3.4. Examples

The following examples shows Session Attributes as they can be set by the Login Service using HTTP Headers.

Basic

name="TestHeader1", path="/d1", value="V1", usage="prop-header"

Causes the SRManager to generate a header named "TestHeader1" having value "V1" for each access to location /d1 and below.

usage="gw-param", name="HGW_Host", path="/d1", value="as.foo.com:1234"s

Exact Match

usage="prop-header", name="TestHeader1", path="/d1",   value="V1"
usage="prop-header", name="TestHeader1", path="/d1/d2", value="V2"

This sample shows the "most exact match" rule applied by the SRManager.. The attributes cause the SRManager to generate a HTTP header named "TestHeader1" having value "V1" for each access to location /d1 and below not including location /d1/d2 and below. The value used for location /d1/d2 and below is "V2"

usage="prop-header", name="TestHeaderValue", value="==Value==",       path="/d1/member",  vtype="value"
usage="prop-header", name="TestHeader1",     value="TestHeaderValue", path="/d1/member" , vtype="ref"
