Chapter 1. Troubleshooting Generelles

1.1. Was der 3rd Level Support nicht macht

Die Leute im 3rd Level Support sind Software Entwickler, deren Fokus primär auf der Produkt-Entwicklung liegt. Die Installationen und Projekte bei Kunden sind ihnen kaum bekannt, auch nicht die Informationen, wie man etwa auf diese Kundensysteme einloggen kann.

  • Wo immer möglich sollen daher Abklärungen beim und mit dem Kunden vom 1st Level Support abgewickelt werden, und insbesondere auch die Implementation von Changes auf den Kunden-Systemen. Der 3rd Level Support liefert hierzu lediglich Vorschläge.
  • Falls es doch mal erforderlich ist, dass jemand vom 3rd Level Support direkt auf ein Kunden-System zugreifen muss, sind die Zugangs-Daten möglichst direkt im Jabber oder per Mail zur Verfügung zu stellen (Link zu GUI Login, Username, Passwort). So können längere Such-Orgien im Wiki etc. vermieden werden.

1.2. Was dem 3rd Level Support nicht hilft

  • Meldungen in Tickets wie "Es geht nicht" (was auch immer). Generische Fehlerangaben dieser Art helfen nicht weiter; auf dieser Daten-Basis ist keine Lösung des Problems zu erwarten.
  • Screenshots - sind so gut wie immer absolut nutzlos, da sie meist überhaupt keine technische Informationen zum Fehler enthalten.

1.3. Was gebraucht wird

Folgendes sollte vorhanden sein, wenn ein Ticket an den 2nd / 3rd Level Support weitergereicht wird:

  • Alle nachfolgend genannten Files möglichst im Ticket attachen!
  • Log file(s), je nach Problem (HSP oder SLS) die HSP access / error logs und / oder die SLS Logs (im Falle des SLS möglichst auf TRACE log level)
  • Idealerweise ein Export der Konfiguration des betreffenden Systems als TAR-Archiv (übers GUI unter "Administration" / "Configurations" / "Import/Export").
  • Möglichst exakte Fehlerbeschreibungen (was macht der User, welche Reaktion wird erwartet, was passiert statt dessen).
  • Bei Login-Problemen im Idealfall eine Möglichkeit zum Testen, sprich: Ein gültiger Login Account (muss typischerweise vom Kunden der USP zur Verfügung gestellt werden).

Chapter 2. SLS Debugging

Bei Problemen speziell mit dem Login können die Schwierigkeiten in verschiedenen Bereichen liegen.

2.1. SLS laeuft / laeuft nicht?

Läuft der SLS überhaupt?

Um das zu prüfen, im Browser einfach die SLS URL aufrufen:

/login/sls/auth

2.1.1. HTTP 500 vom HSP

Eine HTTP 500-Seite vom HSP (meist schwarz) bedeutet, der SLS läuft überhaupt nicht. Sowas sollte eigentlich gar nie vorkommen; in dem Fall bleibt wohl nur, eine SSH Shell auf das System zu öffnen und von Hand zu prüfen, wieso der SLS Tomcat nicht startet. Pfad des Tomcat:

/opt/usp/sls/prod/default/

Stoppen / starten der SLS Tomcat Instanz kann man mittels folgendem Script ausführen:

/etc/init.d/sls [stop|start]

Im Standard-Output des Tomcat sollte man dann hoffentlich Hinweise darauf finden, was den Start des Tomcat verhindert. Dieser Output findet sich in diesem Log-File:

/opt/usp/sls/prod/default/logs/catalina.out

2.1.2. Fehlerseite des SLS

Erscheint hingegen eine Seite mit einer Fehlermeldung des SLS betreffend fehlgeschlagenem Start, dann läuft der SLS zwar als Dienst, ist aber in einem nicht benutzbaren Zustand. Grund dafür ist meist eine inkonsistente / widersprüchliche Konfiguration. Wenn etwa ein- und dasselbe Konfigurations-Property zweimal gesetzt ist, mit unterschiedlichen Werten.

Dies sollte zwar auch nicht geschehen, ist aber in älteren Appliance-Releases durch Bugs im GUI vereinzelt der Fall gewesen. Oder wenn SLS Konfigurationen per SSH von Hand ausgeführt wurden.

2.2. Login funktioniert nicht

Wenn sich User anscheinend nicht anmelden können, obwohl es eigentlich funktionieren müsste, am besten TRACE Logs von einem betroffenen User sammeln und analysieren. Dazu wie folgt vorgehen:

Im GUI unter "Security Realm", "General Settings" bei "TRACE Log for users" den Login-Namen eines betroffenen Benutzers eingeben. Bei älteren Appliance Releases gibt es dieses Setting noch nicht im GUI. Da muss man es als "Custom Property" setzen:

log.trace.enable=amueller,bmeier

Man kann eine Komma-separierte Liste von Login IDs definieren. Sobald der SLS eine dieser IDs erhält, wird für die betroffene Session TRACE-Logging eingeschaltet. Dies hat den Vorteil, dass für den SLS insgesamt alles auf INFO oder ERROR Log-Level gesetzt bleiben kann, und nur kurze Zeit für eine einzelne Session das Performance-Intensive und Platzfressende TRACE-Logging aktiv wird.

Dann "Save" und "Deploy". Nun schaltet der SLS für die Session des entsprechenden Users "TRACE" Log-Level ein, sobald das Username Credential einmal geschickt wurde.

Nun dem User mitteilen, er solle den Login versuchen, und dabei wenn möglich zuerst mal nur den Usernamen in der Login-Seite eingeben und diese so abschicken. Der SLS aktiviert dann aufgrund des Usernamens das TRACE-Logging für diese Session. Dann soll der Benutzer den Login durchführen.

Das TRACE-Log (im "Main log" bzw. "sls.log") kann nun zur genauen Analyse angeschaut bzw. an den 3rd Level Support gegeben werden.

2.3. Log Aggregierung / Korrelation

Alle Requests die durch den HSP laufen erhalten einen sog. "Request Correlator" auf allen betroffenen Back-End Systemen (und HSP Komponenten). Dieser Request Correlator (kurz RC) wird als HTTP Header eingefügt, und jeweils überall geloggt, etwa in access logs etc.

Daneben gibt es auch einen "Client Correlator", der quasi der Session eines Clients entspricht. Auch dieser Wert (CC) wird als HTTP Header in allen Requests eingefügt.

Auf diese Weise können die Log-Einträge von verschiedenen Komponenten wie HSP und Target Applikation betreffend einem bestimmten Request, oder alle Request eines bestimmten Clients miteinander korrelliert werden.

Man muss dazu nur alle Log Files sammeln (HSP, SLS, Applikation) und kann dann mit simplem "grep" Kommandozeilen-Tool alle Log-Einträge zu einer Session oder einem Request heraus filtern.

Vorgehen

Wenn ein Kunde Probleme meldet, die analysiert werden müssen, ist das beste Vorgehen das folgende:

  • Betroffenen Benutzer nach der Login-ID fragen
  • Im Audit-Log des SLS den Log-Eintrag für den Login dieses Benutzers suchen. Grund: Damit fängt die Session des Benutzers ja an. In diesem Log-Eintrag findet man auch den Client-Correlator (CC). Dieser Steht in einem Feld _[CC:<correlator>]_in der Log-Zeile.
  • Nun kann man mit diesem CC in allen anderen Logs (HSP, Applikation) nach den Requests aus dieser Session gezielt suchen. Etwa indem man den CC-Wert als Such-Filter im Log-Viewer eingibt.

2.4. Performance Logging

Es gibt ein SLS Performance Logfile in welchem pro Request eine Zeile geschrieben wird, mit Informationen über den Zeitverbrauch bei der SLS-internen Verarbeitung. Dies gibt Aufschluss darüber, in welchen Teilen der SLS Logik, oder bei welchen Back-End Call-Outs (z.B. LDAP) wieviel Zeit verloren ging.

Ein typischer Log-Eintrag bei einem LDAP Login würde ungefähr so aussehen:

2009-03-13 ... - [Request: 505 [do.auth: 449 [ldap: 446] ] [do.success: 56] ]

Jeweils ein gemessener Schritt im SLS (etwa ein State im Modell) steht in eckigen Klammern, mit der Zeit-Angabe in Millisekunden dahinter. Solche Schritte können auch verschachtelt sein, da etwa der "do.auth"-State im Modell einen Back-End Call macht, und dieser separat gemessen wird.

Im obigen Beispiel sieht man, dass der "do.auth"-State insgesamt 449 Millisekunden Verarbeitungszeit benötigte. Davon entfielen 446 Millisekunden auf den eigentlichen LDAP Call.

Wen ein Kunde angebliche Performance-Probleme mit dem SLS meldet, kann dieses einfache Hilfsmittel schon reichen und zu erkennen, ob die Verarbeitung tatsächlich im SLS selber viel Zeit verschlingt, oder ob es einfach das Back-End Authentisierungs-System ist, welches den Login ausbremst.

Der "do.success" State ist dann üblicherweise der finale State bei einem erfolgreichen Login. Oft verschlingt dieser State im Vergleich zu den anderen übermässig viel Zeit, weil dort noch viele "teure" Operationen ausgeführt werden, wie etwa Krypto-Operationen bei der Erstellung von Login-Tickets etc.

2.5. SLS Logs fuer 3rd Level Support

Wird eine Support-Anfrage betreffend SLS an den 3rd Level Support weitergereicht, sollten folgende Dinge möglichst bereitgestellt werden:

  • Alle SLS Log Files, die im GUI unter "Events" / "Base server" / "Secure Login Service" zu finden sind.
  • Dabei sollte wenn möglich zumindest für den betroffenen Benutzer ein TRACE-Log vorhanden sein (siehe "2.2 Login funktioniert nicht")
  • Die Konfiguration des SLS; am besten einfach einen "Export" der gesamten Konfiguration unter "Administration" / "Configurations" / "Import/Export" als TAR-Archiv.
